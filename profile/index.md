# 工时数据清洗进入系统计划

## 背景

内部工时登记数据是目前最整齐的数据（在飞书登记）：有制度、有格式、有持续积累。工时登记理论上是**绩效数据的起点**——每一次工时背后是真实发生的行为与成果，清洗结构化后，既可以支撑薪酬结算，也可以聚合为绩效记录的行为成果。

## 目标

把飞书中的工时登记数据清洗为统一结构的工时记录，进入系统（qtcloud-human），成为薪酬结算与绩效记录的共同数据底座。

```
飞书工时登记（原始）
  → 清洗（去噪、补字段、校验）→ profile/ 工时记录（结构化）
  → 薪酬：按人 × 职级时薪 → 弹性薪资结算
  → 绩效：按人聚合 → 行为成果记录（时间、事项、结果）
```

## 数据源现状

- **载体**：飞书（工时登记）
- **登记习惯**：已有稳定格式（"工时还是按以前的填"），但字段口径未书面化
- **纪律约束**：有效工时制度——"没有交接文档，一律不算有效工时"；计件工作需审批（企业微信，现已迁飞书）
- **范围**：按人、按日/按任务登记，跨多个周期

## 清洗契约（schema 草案）

清洗产物 = 工时记录（`TimeRecord`），建议字段：

| 字段 | 类型 | 说明 |
|------|------|------|
| `id` | string | 记录唯一标识 |
| `date` | string | 登记日期（YYYY-MM-DD） |
| `person` | string | 人员（姓名/代号） |
| `task` | string | 事项（做了什么） |
| `hours` | number | 有效工时（小时，保留 0.5 粒度） |
| `type` | enum | 计时 / 计件（数字资产、手册等，需审批） |
| `evidence` | string? | 证据：交接文档/产出物链接（有效工时纪律） |
| `note` | string? | 备注（如审批单号、特殊情况） |

口径待定项（需团队确认）：
- 任务粒度：按日登记还是按任务登记（同一人一天多任务如何拆分）
- 无效工时处理：登记了但不计薪的记录是否保留（保留作绩效参考）
- 人员标识：实名还是代号（推荐信场景用代号）

## 清洗流程

1. **导出**：从飞书导出工时登记（表格/API），含时间范围与人员清单
2. **清洗**：脚本处理——去重、去噪、补全（类型/证据）、格式统一
3. **校验**：产出校验报告（条数、人员、工时合计、异常清单），与登记方核对
4. **入库**：产物落 `data/roadmap/profile/`，系统侧替换 mock 或经 API 读取

## 数据流向与系统侧对接

- 系统当前 schema 可作参照：`assets/mock/compensation.json`（workRecords：日期/任务/小时数）、`assets/mock/records.json`（行为成果：时间/事项/结果）
- 清洗产物可直接替换 `workRecords`；按人聚合后生成行为成果记录（绩效起点）
- 页面代码无需改动，mock 替换即生效；后续接 Provider API 时以同一契约
